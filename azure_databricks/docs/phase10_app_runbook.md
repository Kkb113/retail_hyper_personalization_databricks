# Phase 10 — Retail chat assistant

Status: **IN PROGRESS — live deployment blocked**. A stopped App definition is not
a deployed application. Do not report Phase 10 acceptance or move to Phase 11 yet.

## Implemented in this branch

- Single React/Vite chat screen, following the user's clarified scope. No sidebar,
  dashboards or separate tool screens. Recommendations appear in the conversation;
  sources and recommendation details are collapsed. A small authorized-customer selector
  sets demo context. Enter sends; Shift+Enter adds a line; New chat resets the session.
  No invented customer records, metrics, product imagery or prices.
- FastAPI boundary reauthenticates forwarded Databricks OAuth on every protected
  request. Server-owned entitlements are keyed by verified SCIM ID; client-supplied
  grants, customer access outside the allowlist and raw SQL are rejected.
- Secure HttpOnly SameSite session cookies, CSRF confirmation, request byte bound,
  one operation at a time, 20 sessions, 100 operations per process and a fixed lease.
- Existing Phase 8 tools and Phase 9 Luna planner are reused. SQL/feedback uses
  user authorization, not operator credentials. The runtime rejects Azure CLI auth.
- The retained backend feedback endpoint is structured, requires confirmation, and is tied to a batch recommendation
  actually returned in that session. An idempotency key is generated by the server.
  No offline queue claims a write was saved. The existing Delta store remains the backend.
  The simplified UI does not expose a feedback form; do not claim chat saves feedback.
- The retained scenario comparison utility identifies added, removed, unchanged and reranked products.
  Scenarios do not modify persisted profiles. A stopped real-time endpoint fails closed.
- Source currency stays unspecified. Active promotions are the only supported
  opportunity type; replenishment/cart/price-change triggers are explicitly not live.
- Local production build and Python/JavaScript tests. CI now gates on the UI build,
  dependency audit and existing clean-runtime checks. Browser accessibility and live
  OBO interaction tests are not yet accepted.

## Required IT-admin action

The subscription reports `Microsoft.Automation` as `NotRegistered`. A subscription
administrator must register that resource provider. This is outside the authorized
resource-group-only mutation boundary, so this branch does not do it automatically.

In Azure Portal: **Subscriptions → target subscription → Resource providers →
Microsoft.Automation → Register**. Alternatively, the administrator can use:

```powershell
az provider register --namespace Microsoft.Automation --wait
```

They must first select the correct subscription. Registration is not deployment of
an Automation account, and does not itself implement shutdown.

## Remaining release gates after registration

1. Create one Basic Azure Automation account in the approved RG and a dedicated
   managed-identity stop-only runbook. No hybrid worker VM, Log Analytics workspace,
   public webhook or recurring idle job. Verify current pricing and provider availability
   before creation. The subscription-wide free minute allowance may be shared.
2. Test the runbook's identity and exact App/warehouse/endpoint stop permissions.
   Arm and verify the independent controller before any paid start. Prefer a short,
   fixed demo window (initially 10 minutes), not an always-on service. Keep stop
   retries bounded, alert on failure, and verify terminal STOPPED states.
3. Bind App resources and approved OBO scopes; supply a private server-owned
   entitlement mapping, persistent actor HMAC secret and bounded release lease.
   Grant only required governed views/feedback access. Prove App principal cannot
   read raw tables and two user identities cannot cross customer entitlements.
4. Complete the cloud entrypoint/deployment package, exact static asset and wheel
   hashes, dependency lock verification, immutable release manifest and rollback path.
   The current loopback preview is deliberately disconnected and is not that entrypoint.
5. Run one bounded live acceptance window: Luna workload inference, batch cards,
   semantic discovery, what-if parity, feedback read-back/replay, OBO denial,
   stale-session/cold-dependency behavior, browser keyboard/responsive checks and
   stop-controller failure recovery. Stop everything and record actual elapsed time.

## Cost boundaries

No Phase 10 paid compute starts or inference calls were made during this bootstrap.
Existing storage and other subscription resources can still incur charges; this is
not an assertion of a zero invoice. Managed-resource-group costs remain unreconciled.

Medium is currently the smallest App size (0.5 DBU/hour). An App lease only rejects
requests; it does **not** stop billable compute. A running-state check before SQL reduces
accidental wakeups but is not an atomic prevention of a stop/query race. The independent
stop controller and final STOPPED verification remain mandatory.

Do not reuse/reset the Phase 9 spending ledger. Finalize a separate cumulative Phase 10
validation ledger and conservative INR estimate before paid testing. Budget alerts are
not a hard invoice cap. No premium upgrade, additional SQL warehouse, Lakebase,
Vector Search endpoint, separate hosting service or provisioned LLM throughput is needed.
